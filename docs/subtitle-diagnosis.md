# YouTube 原生字幕诊断

更新时间：2026-09-02。本文件只描述当前架构的故障定位方法。

## 正常链路

1. YouTube 页面请求 `/api/timedtext`。
2. 后台确认请求属于合法视频和字幕轨，读取响应正文并保存会话缓存。
3. 后台向对应标签页发送 `captured`。
4. 内容脚本立即解析正文并更新侧栏；重连时通过 `latest` 优先恢复最近捕获结果。
5. 没有可用缓存时，内容脚本从第 0ms 开始请求所选轨，同时观察授权字段；授权出现后立即重试。
6. Side Panel 收到原始 cues 和派生 phrases，最终 DOM 完成状态门禁。

## 过去故障的直接原因

- 内容脚本曾轮询“所选轨正文缓存”，而不是检查已经捕获的授权字段。网页先请求另一种轨道时，授权已可用但缓存键不匹配，造成无意义等待。
- 后台曾只保存和广播捕获结果，内容脚本没有消费 `captured`；连接或刷新时也没有查询 `latest`，所以网页已经取得字幕但侧栏仍停在准备状态。
- 旧显示路径在失败时会回退到碎片化原始块，造成完整问句被拆成独立短行。

当前提交已经通过生产 bundle 回归覆盖上述三类问题：捕获即时推送、重连缓存优先、拒绝/超时/畸形缓存继续正常请求，以及短行 DOM 门禁。

## 诊断时间线

速度问题必须记录四个时间点：

1. 网页 timedtext 请求完成。
2. 后台缓存正文完成。
3. 标签页收到 `captured`。
4. Side Panel 第一行完成渲染。

没有这四个时间点，不能把故障归因于网络慢、缓存早晚或分句耗时。

## DOM 验收条件

完成状态必须同时满足：

- 内容脚本 `status=loaded`。
- `phraseCount` 等于预期值。
- Side Panel 根容器 `data-display-mode=phrases`。
- 每个字幕节点都能解析 `startMs/endMs`。
- `endMs - startMs >= 2000`，即 `underTwoCount === 0`。
- 核心目标句完整存在。
- `single one?` 和 `wrong.` 不存在独立行。

只看到首个 `.echo-cue`、只比较内存数组或只拍截图，都不足以判定通过。

## Service Worker 重载条件

- 调用 `chrome.runtime.reload()`。
- 等待旧 Worker `close`，记录旧实例退出时间。
- 确认新 Worker 使用不同实例令牌上线，并经过稳定等待。
- 对生产源、加载目录和运行时的关键文件分别计算 SHA-256，三方必须一致。
- 若命令行加载的扩展不能在同进程重新注册 Worker，应关闭旧测试进程并以同一 Profile/加载目录重启；不能把磁盘更新冒充运行时重载。

## 证据等级

当前 24/24 证据属于 `test-browser real-data replay`。Chrome for Testing 没有暴露原生 Side Panel page target，因此测试在真实生产 `sidepanel.html` 页面执行 DOM 与交互断言；这不覆盖用户当前 Chrome 的 `installed-real`，也不等于实时网络端到端验收。

遇到失败时按“表现、直接原因、根本原因、影响、已做修复、仍需验证”记录，不使用口头成功承诺替代断言输出。
